# Axon

Axon is a scientific programming language; this repository is its interpreter, written in Delphi.

## Documents

The design lives in `doc/`. The Language Reference is the authority on behaviour; where the milestone plan and the reference disagree, the reference wins.

- `doc/Axon-White-Paper.md`: rationale and examples
- `doc/Axon-Language-Reference.md`: exact syntax and semantics. Its Contents section is generated: after adding or renaming a `##`/`###` heading, run `python tools/gen_contents.py doc/Axon-Language-Reference.md` (anchors match the IDE viewer's `RhoHeadingSlug` and GitHub)
- `doc/Axon-Milestones.md`: build order (M0–M13) and what each milestone's tests must cover
- `doc/Axon-JIT-Plan.md`: the L2 MIR JIT plan (decisions D1–D7, milestones J0–J12)
- `doc/research/augmented-steady-state/`: a research project (not part of Axon): steady states with conservation laws solved without reduction, N v(y) + K (K'y - K'y0) = 0. `README.md` is the project description (theory with proofs, experiments, limitations, work plan, how to resume); `python/` holds a reference implementation and experiments E1-E11 (`python experiments.py`, results in `results.txt`)
- `doc/manual/axon-manual.tex`: the LaTeX user manual (language and IDE). Its longer examples are files in `doc/manual/examples/`, included with `\lstinputlisting`; their figures go to the gitignored `doc/manual/figures/`. `tools\build_manual.cmd` runs the examples with Release `axon`, then LaTeX (latexmk, or pdflatex three times without Perl). Every listing must run as printed: rerun the examples after language changes

## Build and test

- `build.cmd` builds Win64 Debug (`build Release` builds Release) with RAD Studio 37.0. Output goes to `Win64\<Config>\axon.exe`.
- In RAD Studio, open `Axon.groupproj` and use Build All: it builds `axon.dproj` (whose post-build step puts the DLLs, stdlib, examples and help into `Win64\<Config>`), then `ide\AxonIDE.dproj` into the same folder.
- macOS: both projects target OSXARM64, and PAServer deploys the IDE bundle. The IDE runs `axon` and reads `stdlib/`, `examples/` and `help/` from `Contents/MacOS`, so `AxonIDE.dproj`'s Deployment section lists each of those files, and the dylibs in `lib/macos` (see `lib/README.md`; `libopenblas.dylib` comes from `tools/build_openblas_mac.sh`, run on the Mac): after adding or removing an example, help page or stdlib file, run `python tools/gen_mac_deploy.py` (with the project closed in RAD Studio, which rewrites the .dproj when it saves). Build `axon` for OSXARM64 in the same configuration before deploying.
- Version: `src/Axon.Version.pas` holds `AxonVersion`; `AxonVersionText` adds the build time and git commit from `src/Axon.BuildInfo.inc`, which `tools/AxonBuildInfo.targets` (imported by both projects) writes on every build (gitignored; `+changes` marks uncommitted edits). `axon --version`, the IDE's Welcome tab and Help > About show it, to check which build is deployed.
- `test.cmd` runs every test; `test.cmd -v tests\m03` runs one milestone and lists passes as well.
- From PowerShell, give the scripts by full path, because `cmd /c` does not search the PowerShell location: `cmd /c "$PWD\build.cmd"`, then `cmd /c "$PWD\test.cmd"`.
- macOS builds go through PAServer from the IDE. The POSIX code in `Axon.Platform` can be syntax-checked locally with `dccosxarm64` / `dccosx64`.

## Layout

- `axon.dpr`, `axon.dproj`: console program
- `src/Axon.Cli.pas`: command line (`axon file.sci`, `--tokens`, `--ast`, `test`)
- `src/Axon.Errors.pas`: `EAxonError` with error kinds, and the process exit codes
- `src/Axon.Platform.pas`: the only place for `{$IFDEF MSWINDOWS}`/`POSIX` code, apart from `src/native`
- `src/Axon.TestRunner.pas`: `axon test`
- `src/Axon.Lexer.pas`, `Axon.Parser.pas`, `Axon.Ast.pas`, `Axon.AstDump.pas`: the front end. Triple-quoted strings are read by `LexTripleString` (raw text, then the first line break dropped and the shared indentation removed, then `Unescape`)
- `src/Axon.FloatParse.pas`: decimal text to the nearest double for real literals (Clinger's fast path, else Go strconv's decimal-shift algorithm). Delphi's `TryStrToFloat` is not correctly rounded; don't use it for literals. `TryParseReal`/`TryParseInt` there read numbers from text (sign, spaces, NaN/Inf) for `real(s)`, `int(s)` and CSV.
- `src/Axon.IoModule.pas`: the core module `io`: whole files, `read_lines`, CSV (`read_csv` returns `{names, data}`; `write_csv` writes reals in the shortest form that reads back exactly) and JSON through `Axon.Json`. The string built-ins `split`, `join`, `trim` are in `Axon.Builtins`
- `src/Axon.Values.pas`: `TAxValue`, a tagged record holding scalars inline and other payloads in reference-counted objects; also the display forms. Displayed reals go through `ShownReal`, which applies `fmt.set_decimals` (`DisplayDecimals`, with `DisplayRows`/`DisplayCols` for `fmt.set_size`; `DisplayHeader` for `fmt.set_header`; `SciSmall`/`SciLarge` for `fmt.set_sci`, applied by `DisplayReal`); error messages use `FormatReal`, which ignores the settings (fixed limits 1e-4 and 1e15). Exact fixed-decimal text (`format`, `fmt.set_decimals`) is `FormatFixed` in `Axon.FloatParse`
- `src/Axon.Ops.pas`: operators, promotion, checked integer arithmetic. Array and range operands are passed on to `Axon.Arrays`.
- `src/Axon.Arrays.pas`: dense arrays. `TArrayObj` (declared in `Axon.Values`) is column-major, with one typed buffer per element type. This unit holds literals, broadcasting, `MatMul`, transpose, index resolution and reductions. Elementwise operations are defined as the scalar operators applied per element (`Broadcast2`, `MapArray`); the "fast paths" section (`FastBinaryOp`, `RealLoop`, `FastNegate`, `FastFold`) runs the bool/int/real cases as typed loops that must give bit-identical results and errors (same summation order, overflow checks, NaN rules, result element types, empty results left to the general code), and `Axon.Builtins` does the same for elementary functions on arrays, `min`/`max` of one array and `sort`/`sortperm` (stable; NaN last). `tests/m13/array_fast_paths.sci` checks them against element-by-element results. `bench/vs_python.py` (with `bench/vs_python.sci`) times Axon against CPython, NumPy and SciPy.
- Assignment to `a[i].f[j] = v` and similar goes through `AssignPath`/`SetIn`. `SetIn` walks the path, calling `MakeUnique` on each level before writing; that function copies one level of a list, record or dictionary when it is shared. Arrays at the leaf go to `AssignArraySlot`.
- `v = append(v, x)` statements run through `TInterpreter.ExecAppendAssign`: the value is taken out of `v`'s cell while `AppendInPlace` (`Axon.Builtins`) grows the list or vector in place if its reference count is then 1 and no wider element type is needed; otherwise `AppendValue` builds a new value, as the plain call does. Compiled code does the same for lists (`rt_list_append`, J10); `append` on vectors stays interpreted.
- Copy-on-write: `AssignArraySlot` clones an array when `RefCount > 1`. Never keep an extra `TAxValue` copy of the target array alive while deciding, or every write will copy. `__copies()` counts clones for tests.
- `src/Axon.Complex.pas`: complex arithmetic and principal-value functions
- `src/Axon.Builtins.pas`: prelude functions. A built-in may take keyword parameters after a fixed number of positional ones (`TBuiltinObj.KwNames`, the `Add` helper's last argument): `CallBuiltin` checks the names and passes their values after the positional arguments, `nothing` for one not given (`isapprox(a, b; rtol, atol)` is the first)
- `src/Axon.Interp.pas`: tree-walking evaluator and scopes. Constructs from later milestones raise `ENotImplemented` (exit code 2).
  - Scopes are reference-counted by hand (`AddRef`/`Release`), because closures keep their defining scope alive.
  - Variables are `TVarCell`s, which carry the type annotation and the `global` marker.
  - A function stored in the scope it closes over forms a cycle that is never freed. That's accepted for now.
- `src/Axon.Repl.pas`: the REPL (commands `help name` and `run "file"`; `run` uses `TInterpreter.RunInSession`, and the IDE's Run in REPL button and Shift+F9 send it) (`axon` with no arguments; prompts `> ` and `... `), and `axon --transcript file`, which replays the `> `/`... ` lines of a transcript and writes the session, errors included, to stdout.
- `src/Axon.Help.pas`: the REPL's `help name`. Function headers come from the source text (`ParseSource` in `Axon.Parser` stores `TFunctionDecl.Header` for top-level functions); built-ins are described by a table in this unit, so add a row when adding a built-in. Keywords (`help for`) have their own table (`KeywordDocs`, `KeywordHelp`): the form unindented, the description indented by two spaces, examples by four; the IDE's `HelpMarkdown` shows unindented and four-space lines as code, and `ide/uRefSections.pas` maps keywords to Reference sections too. A `##` block that opens a file and is followed by a blank line is the module docstring (`TProgram.Doc`).
- `src/Axon.Packages.pas`: reads `package.toml` (a TOML subset, cached per directory) and resolves module files. `Axon.Interp` loads modules (`LoadModule`, `ExecImport`). Each `TModuleObj` has its own module-root scope, and functions remember their file, so calls switch `FFile`/`FCurrentPath` for error reports and nested imports.
- `src/Axon.Ffi.pas`: `extern`. Calls go through `System.Rtti.Invoke` (no libffi), with argument and result conversion and `ref`/`ptr`/`cstring` handling. Callback errors are held as pending and raised after the native call returns.
- `src/native/Axon.Native.Callbacks.pas` and the generated `Axon.Native.Trampolines.pas`: a fixed pool of callback trampolines (32 per return kind). Regenerate the trampolines with `bash tools/gen_trampolines.sh`; never edit them by hand. Win64 uses inline-assembly stubs that spill the registers into the caller's home area; macOS uses Pascal functions taking 8 integers and 8 doubles.
- `tests/m09/native/axontest.dpr`: the native test library, written in Delphi. `build.cmd` builds it into `tests/m09/bin` (gitignored).
- `src/Axon.Linalg.pas`: the core `\`, `/` and matrix `^`, and the BLAS product behind `*`, through `src/native/Axon.Native.Blas.pas` and `Axon.Native.Lapack.pas`. Those units load OpenBLAS on first use, so the interpreter still starts without it.
- `src/Axon.Sparse.pas`: sparse matrices (`TSparseObj`, CSC, declared in `Axon.Values`). Values are always stored as `TComplex` with an `IsComplex` flag. Holds construction from triplets, sparse arithmetic, the dispatch for operators with a sparse operand (`Axon.Ops` checks for sparse before arrays) and `S \ b`. Indexing and assignment are in `Axon.Interp` (`IndexSparse`, `AssignSparseSlot`); overwriting an existing entry is done in place after copy-on-write, anything else rebuilds the matrix.
- `src/Axon.SparseLU.pas`: the sparse LU, written in Delphi so that no SuiteSparse library is needed: minimum-degree ordering on A + A' (degree buckets), then left-looking Gilbert–Peierls factorisation with threshold partial pivoting that prefers the diagonal.
- `src/Axon.NativeModules.pas`: core modules written in Delphi. `import m` uses one when no `m.sci` is found; `Axon.IoModule` (`io`) and `Axon.Graphics` (`graphics`) register themselves in their `initialization` sections. Add help rows for their functions to the table in `Axon.Help`.
- `input(prompt)` (`BInput` in `Axon.Builtins`) reads a line from standard input (`nothing` at its end). With a display channel (the IDE), it ends the prompt's line with U+0005 and a newline; the IDE (`AddOutputLine` for runs, `ReplOutput` for the REPL) shows that line with an input box (`FRunInput`, or the REPL's next line, `FReplAwaitInput`) and writes the answer to the process's stdin (runs start with an input pipe). The test runner gives a test `name.in` as its standard input (`RunProcess`'s `StdinFile`).
- `src/Axon.TimeModule.pas`: the core module `time` (`clock`, `now`, `sleep`, `elapsed`, `bench`, `format`). `elapsed` and `bench` call Axon functions through `CallAxon` in `Axon.NativeModules`, a hook the interpreter sets to its `CallValue` when it is created (one interpreter per process).
- `src/Axon.Random.pas`: the core module `random` (`seed`, `rand`, `randn`, `uniform`, `normal`, `randint`; parameters first, then an optional shape) and the generator behind the prelude's `rand` (xoshiro256** seeded with SplitMix64, from the clock at start-up). `tests/m13/random_module.sci` checks seeded draws against values from an independent implementation; keep the algorithm fixed, or recompute them.
- `src/Axon.Scene.pas`: the scene model shared by `axon` and the IDE (doc/Axon-Display-Plan.md): `TScene`/`TSceneItem` (plain Delphi classes, no interpreter units; images already as RGBA pixels), the Skia drawing of a scene onto any canvas (`DrawScene`), `SavePng`/`SaveSvg`/`SavePdf`, text measuring, and a binary encoding (`EncodeScene`/`DecodeScene`, magic `AXS1`, doubles for coordinates). `AXON_SCENE_ROUNDTRIP=1` makes `axon` encode and decode every scene before drawing, to check the encoding against saved pictures. The display channel: the IDE's `TProcessRunner.Start(..., WithDisplay)` gives a program or the REPL one more pipe, named by `AXON_DISPLAY` (the inherited handle's number on Windows, set only around `CreateProcess`; fd 3 on macOS); `axon` writes messages to it (`Axon.Platform.DisplaySend`: UInt32 length, kind byte, payload; kinds `DisplayShow`, `DisplayFrame`, `DisplayFigure`, `DisplayAdd` in `Axon.Scene`; `DisplayAdd` carries only the items added to the current frame, which `graphics.frame(scene, sent)` sends and `draw.frame` uses when the canvas was not restarted, and the IDE appends them to the animation's scene, never skipping one), and `graphics.show`/`frame` use it instead of files when it is there (returning nothing). A `TDisplayThread` reads whole messages and delivers them through `OnDisplay`; `TfrmMain.DisplayMessage` turns them into `TFigureEntry` history items (scene, figure JSON, or file path) drawn in `FPlotScene` (a `TSkPaintBox`) or the charts.
- `src/Axon.Graphics.pas`: renders a scene (an Axon record of drawing items: polylines, polygons, rects, circles, ellipses, arcs, markers, text, images, and groups that shift, turn, scale and clip) to PNG, SVG or PDF through Skia's flat C API (`System.Skia.API`). This unit checks a scene record and converts it into an `Axon.Scene` `TScene` (`MakeScene`; fields read in the same order as before, so the same first error is reported), which then draws and saves it. Strokes are `TStroke` (width, dash, cap, join; `StrokeField` reads an item's). An `image` item's colours are worked out here: an RGBA8888 unpremultiplied pixel buffer from a `values` matrix and a colour map (viridis, gray, hsv, or a table) or from red/green/blue matrices; `Axon.Scene` draws it with `sk4d_canvas_draw_image_rect` (nearest-neighbour unless `smooth`). Don't use the high-level `System.Skia` unit: its class constructor loads `sk4d.dll` at start-up and aborts if it is missing. Here `SkInitialize` runs at the first call. On macOS Skia is linked statically.
- `stdlib/ode.sci` and `src/Axon.OdeCore.pas`: `ode.solve` checks its arguments and builds the result record and `sol.at` in Axon; the stepping loops run natively in the core module `odecore` (`odecore.rk45`, `odecore.bdf`), which reproduce the former Axon loops operation for operation (compare results bit for bit when changing them). BDF calls CVODE from Delphi (`src/native/Axon.Native.Cvode.pas`, loaded on first use) with cdecl callbacks that find their solve through CVODE's user data; a callback keeps any exception and returns -1, and the loop re-raises it. `f` and event functions are called through `CallAxon`, so compiled right-hand sides run natively. With `params` set, `TOdeBase.Rhs` and `Event` pass it as a third argument. `ode.integrator`/`ode.advance` (`odecore.integrator`/`advance`) keep a solver alive between calls: the handle is a `vkPointer` value whose `Obj` is a `TIntegratorObj` (freed with the last copy), holding a `TRk45Engine` (DOPRI5 one step at a time, stepping past the target and interpolating) or `TBdfEngine` (CVODE in `CV_NORMAL`, `CVodeReInit` on restart); `TStepEngine.Advance` continues only when (t, y, params) equal what the last call returned, otherwise restarts. These are separate from `TRk45.Run`/`TBdf.Run`, whose results must stay bit for bit. CVODE's vectors are copied with `memcpy` from `libc`, which `stdlib/package.toml` maps per platform.
- `stdlib/nonlin.sci` and `src/Axon.NonlinCore.pas`: `nonlin.solve(f, x0)` solves f(x) = 0 with SUNDIALS KINSOL (`src/native/Axon.Native.Kinsol.pas`, loaded on first use; its functions are fields of the record `Kin`, because `Axon.Native.Cvode` binds the same SUNDIALS names from its own library). `nonlin.sci` checks the arguments; the native core module `nonlincore` (`nonlincore.kinsol`) runs KINSOL as `odecore` runs CVODE: `f` called through `CallAxon` (with `params` as a second argument when given), its exception kept and re-raised after `KINSol` returns, a non-finite value returned to KINSOL as recoverable. Settings that matter: a new Jacobian every iteration (`KINSetMaxSetupCalls(1)`, full Newton; KINSOL's default modified Newton took 3x the iterations) and no cap on the Newton step (`KINSetMaxNewtonStep(1e150)`; the default, 1000 |x0| but at least 1, made starts from zero crawl).
- `stdlib/antimony.sci`: the `antimony` module, written in Axon only: reads a basic subset of Antimony (reactions with rate laws as text, numeric assignments, `$X` boundary species: in `Model.boundary`, no row in N, their values after the parameters in `_p`, `parameter_names`) into `Model`/`Reaction` records and simulates them. `rhs_text` writes the whole right-hand side as the text of one function `f(_t, _y, _p)` and `rhs` makes it with `parse_function`, so the JIT compiles it; parameter values come from the vector `_p`, which `ode.solve` passes through its `params` keyword (no closure, so the compiled function is called directly). `simulator`/`step`/`set` advance a simulation in steps through `ode.integrator`/`ode.advance`. `conservation` is the conservation analysis (Reder; Sauro and Ingalls 2004; Vallabhajosyula, Chickarmane and Sauro 2006): independent species from QR with column pivoting of N' (`linalg.qrp`, LAPACK `geqp3`), L0 = (R11 \ R12)', link matrix and gamma = [-L0 I] in species order. `steady_state` solves for the independent species by default (`method = "reduced"`); `method = "augmented"` solves N v(y) + K (K'y - K'y0) = 0 for every species, K = `linalg.null(N')`, whose Jacobian is singular exactly when the reduced one is (the manual's section "Conservation laws and the link matrix" has the argument). `jacobian`/`reduced_jacobian` are central differences of `rhs`. Metabolic control analysis (`doc/Axon-MCA-Plan.md`): `rates`/`rates_text` (v(y, p), sharing `rate_lines` with `rhs_text`), `fluxes`, `elasticities`/`parameter_elasticities` (`rate_derivatives`: five-point differences with relative step eps^(1/5), as libRoadRunner), and `control` (a `Control` record: C^S = -L (Nr E L)^-1 Nr, C^J = I + E C^S, scaled by default, NaN where dividing by 0; `unscaled_control` is shared with `response`, the response coefficients R = C P to every parameter, a `Response` record). Example 30 and the manual's section "Metabolic control analysis" (`doc/manual/examples/mca.sci`) show them, printed with `fmt.matrix(A; rows, cols)` and drawn with `plot.bar3` given name lists for `x`/`y` and `clim`. `tests/m13/antimony_control.sci` checks hand-worked cases, the summation and connectivity theorems and perturbation; `tests/m13/antimony_tellurium.sci` compares with libRoadRunner's values in `tests/m13/tellurium/mca_reference.json`, written by `tools/tellurium_mca_check.py` (rerun it if the test models change).
- `stdlib/draw.sci`: the `draw` module, Axon over `graphics`: a current canvas with a view in coordinates with y pointing up (`px`/`py` map to the page), shapes, images, a turtle (module-level state; consecutive moves collect into one polyline, flushed on a pen change, `penup`, `pop`, `scene`), and L-systems (`lsystem` rewrites, `trace` walks a string with `draw`/`move` character sets, `lsystem_path` returns the points, `lsystem_draw` uses the turtle). Items are a separate module list so `items = append(items, x)` grows in place. Like `plot`, an unshown canvas is shown at exit (`atexit`) and when a new canvas starts. Examples 22-26 use it (25 and 26 animate with `draw.frame`).
- `stdlib/colors.sci`: the 140 web colour names (CSS/X11) as 0-255 ints in one `dict` literal, looked up ignoring case, spaces, underscores and grey/gray (`normal`); `rgb` (reals 0-1, as `graphics` takes colours, optional `alpha`), `rgb255`, `hex`, `has`, `names`. Its values are the web's, unlike the 16 palette names `graphics` itself accepts (`"red"` is plot's red).
- `stdlib/fmt.sci` and `src/Axon.FmtCore.pas`: the `fmt` module (display settings `set_size`, `set_decimals`, `set_header`; `number` and `matrix`, with keyword options, return text; `matrix`'s `rows`/`cols` name the rows and columns, as tables). The settings and number formatting are in the native `fmtcore`; the rest is Axon.
- `stdlib/plot.sci`: figures built in Axon and drawn through `graphics`. Every plotting call goes through `figure_now()` (or `figure()`), which sets `changed`; `show` and `save` clear it, and `show_unshown`, registered with `atexit` (`RunAtExit` in `Axon.Builtins`, called at the end of `TInterpreter.Run`, not after an error or in the REPL), shows a changed figure when the program ends, and `figure()` calls it before replacing the current figure. `subplot` keeps the grid in `layout` (cells are ordinary figure records sized to the cell; `current` is the selected cell); `figure_scene` draws each cell with `render` and places it with a `graphics` group's `dx`/`dy`; `show` passes `whole_figure()` (the grid record) as the data, and `ide/uFigureGrid.pas` builds a `TGridPanelLayout` with one `TSkPlotPaintBox` or `TRho3DPlot` per cell, loaded by `LoadFigureObj`/`LoadFigure3DObj` (the record-level halves of `LoadFigure`/`LoadFigure3D`). The plot pane's Copy and Save… draw the figure as it is on screen (`ide/uFigureExport.pas`): each chart draws itself onto one Skia canvas (raster PNG/bitmap, PDF page or SVG canvas) with the components' `RenderTo`, in its place in the grid. `plot.save(path, figure = f)` saves any figure record from Axon. The IDE's plot pane keeps a history of figures (`FFigures`, the newest 50; `AddFigure`, `DisplayFigure`, with ◀/▶/Clear in its header), which `TryShowFigure` and `ShowNewestPlotIn` add to.
- `stdlib/`: the standard library, written in Axon. `linalg.sci` binds LAPACKE through `extern "libopenblas"`. A post-build step copies `stdlib/*.sci` and `stdlib/package.toml` to `Win64\<Config>\stdlib`.
- Tests that write files name them `_tmp_*` (gitignored) and delete them. A milestone test file must not share a name with a module it imports (`io.sci` would shadow `io`).
- Numerical tests compare against reference values with the helpers in `tests/m10/testing.sci` (`approx`, `approx_set`, `orthonormal`), not with exact printed digits.
- Module tests: `tests/m08` holds fixture modules next to the tests. A `stdlib/` folder inside a milestone folder becomes `AXON_STDLIB` for that folder's tests.
- `src/native/Axon.Native.*.pas`: one unit per C library. Declarations are added in the milestone that first uses the library.
- `src/native/Axon.Native.Mir.pas` and `src/native/axmir.c`: the MIR JIT library (L2, `doc/Axon-JIT-Plan.md`). `mir.dll` is MIR's `mir.c` and `mir-gen.c` plus the shim `axmir.c`, built by `tools\build_mir.cmd` (clones MIR v1.0.0 into the gitignored `third_party/mir`, builds with MSVC 2022 through `tools/mir/CMakeLists.txt`, copies to `lib/win64`). Delphi calls MIR's pointer/integer functions directly; operands go through the shim as `TAxMirOp`, because `MIR_op_t`'s bitfield layout differs between compilers; instruction codes are looked up by name (`MirCode`). Loaded on first use (`MirAvailable`). `axon --jit-selftest` (`src/Axon.JitSelfTest.pas`) checks the library.
- `src/Axon.Jit.Ir.pas`, `src/Axon.Jit.Lower.pas`: JIR, the JIT's typed IR, and the lowering of one named function's syntax tree to it, with type inference; anything whose behaviour cannot be fixed statically raises `EJitReject` with a reason and position, and the function stays interpreted. Reads are accepted only where the variable is definitely assigned (the interpreter resolves names at run time, rules 5 and 6). `axon --jir file.sci` prints each top-level function's JIR or why it is rejected; `.jir` tests live in `tests/jNN/` (the test runner accepts `j` folders). Write `.jir` expectations by hand; temporaries are numbered in order of appearance.
- `src/Axon.Jit.pas`, `src/Axon.Jit.Mir.pas`: the JIT's runtime and code generator. Modes `--jit=off|on|force` (a leading option) or `AXON_JIT`; default on (J5). `test.cmd -jit` runs the suite in all three modes. With `AXON_JIT_REPORT` set, each compile decision goes to stderr as a `#3jit compiled name` / `#3jit rejected name: reason (line:col)` line, a rejection followed by a tab and the file; the IDE's Run > Use JIT Compiler (and JIT toolbar button) sets `AXON_JIT` for the processes it starts, saves it as `Jit=` in `settings.ini`, and turns the report lines into notes after each run (`TryJitReport`, `ReportJit`): a rejection in the user's own files is a link to the place (`FJitWhere`, negative item tags) and a red squiggle under that line (`ColorJit`) with the reason as its tip; those in the standard library are only counted. Rejection reasons should say what to change where they can (`TypeChangeHint` in `Axon.Jit.Lower`); the manual's section "When code stays slow" lists the common ones. Edit > Preferences (`uPreferences`) has Show run notes and Show JIT report (`ShowRunNotes`, `ShowJitReport` in `[Preferences]`), which hide those grey notes. The reference's "Compilation" section is the user-facing description of what compiles. With the JIT on, `Invoke` compiles a non-closure function at its first call (`JitCompile`: lower, then generate), keeps the `TJitCode` on the `TFunctionObj`, and calls its entry thunk with the bound arguments in 8-byte slots (`RunCompiled`). Errors leave compiled code by status, never by exception: generated code calls `rt_error` (or a helper records the error) and returns 1, and `RunCompiled` raises the pending `JitError` at its site inside Invoke's frame handling, so reports and traces match the interpreter's. Helpers called from generated code are `cdecl` and must never let an exception escape. `__jit_mode`, `__jit_compiled` and `__jit_reason` are for tests (a test switches the mode to run a function compiled and interpreted); `AXON_JIT_LOG=file` logs each compile decision. Run the suite in all three modes (`AXON_JIT=on`, `force`) after JIT changes. Calls (J3): `TJSession` (Axon.Jit.Lower) lowers functions on demand with a resolver the interpreter supplies (`JitSetup`: names resolve through the function's defining scope; `--jir` resolves statically to the file's functions and the prelude). `GenerateGroup` generates every newly lowered function and links them together; bodies are exported `f<id>` and called directly behind a guard on the module variable, with the interpreter's call-depth counter. Other calls go through `rt_call` (boxing, `CallAxon`). An error records its origin; each compiled caller adds its frame (`rt_frame`); `TakeJitError` rebuilds the interpreter's trace. Elementary built-ins, `atan2`, and `div`/`mod` of reals (`RDivReal`, `RModReal`, shared with `DivMod`) call `ElementaryRealFunction` routines directly. Arrays (J4): `vector{real}`, `vector{int}`, `matrix{real}` (element type must be declared). Each array register is a `TAxValue` slot in an alloca'd frame released at the function's single exit (`rt_leave`); array arguments/results pass as slot addresses; a body takes its own reference to array parameters; moves from temporaries transfer, from variables share, so refcounts and `__copies()` match the interpreter. Element access is inline using `TArrayObj` field offsets measured in `ComputeLayout`; writes check the refcount and call `rt_make_unique`. Array operators go to `Axon.Ops` through `rt_call` (`IsOp`). Specialisation (J6): unannotated (and plain `vector`/`matrix`) parameters take the argument's type; session entries are keyed by function and parameter types (`SignatureFor`/`SignatureKey`), at most `MaxSpecialisations` per function; `Invoke`'s `CompiledFor` types the bound values (`JitTypeOf`) and caches codes per signature on the `TFunctionObj` (last signature checked first); compiled calls specialise the callee on static argument types. Records (J9): `TJType` is an integer type; record shapes (field names, field types, declared type) are interned in `Axon.Jit.Ir`'s shape table from `jtFirstRecord` up (`RecordType`, `ShapeOf`, `JTypeOfValue`), and the call boundary checks values structurally with `JTypeMatches`. Record registers are value slots like arrays (`IsBoxedType`); `joField`/`joSetField` and `joLoad`/`joStore`/`joLen` take a `Path` of field positions, generated inline from `TRecordObj`'s layout (`PathAddr`, copy-on-write with `rt_record_unique` at each record of a write's path); `joRecord` builds literals and constructors through `rt_new_record`, which also checks a constructor's record type was not redefined. Temporaries holding a field's array or record, or stored into a record, are cleared right after use (`ReleaseFieldTemps`, `ReleaseTemps`) so reference counts and `__copies()` match the interpreter's. A write that would change a record's shape rejects the function. Lists (J10): `list{T}` types sit in the same table (`ListType`, `ListElem`, `IsListType`); `list{?}` is the empty list, which matches any list type at a call. An empty literal whose variable is later given a `list{T}` raises `EJitRetry`, and `TJSession.Lower` lowers the function again with the literal's type in `Hints`. `joList`/`joAppend` build and append through `rt_new_list`/`rt_list_append` (in place for `l = append(l, x)` when the list is unique, as `ExecAppendAssign`); `joLoad`/`joStore`/`joLen` on a list base read items inline (`GenListElem`, `GenListLen`: the dynamic array's length before its first element), copy-on-write with `rt_list_unique`. The call-boundary check scans every element (a tight kind loop for numbers). Strings (J11): `jtString` is boxed too; a literal is `joConst`, a `TAxValue` the code owns (`TJitCode.Consts`) copied into its slot; `joConcat`/`joStrCmp` call `rt_str_concat`/`rt_str_cmp` (`CompareStr`, as the interpreter compares); `string(x)` of a number and `length(s)` are `joStrOf`/`joStrLen` (`rt_str_of_int`/`_real`, `rt_str_len`, sharing `Display` and `StringLength` with `Axon.Builtins`); the other string built-ins go through `rt_call` with argument types checked in `LowerStringBuiltin` and result types known; `typeof(x)` is folded to a constant from the static type (`StaticTypeName`). `rt_call` boxes a string argument from its register, or from the literal when `TJitCallSite.IsLit` says the call site holds one. Indexing and iterating strings are rejected. Top-level loops (J12): `ExecStmt` hands a `for`/`while` whose scope chain ends at a module root to `TInterpreter.TryRunLoop`, which compiles it with `JitCompileLoop` as a declaration whose body is the loop (`TLoopJit` per statement, keeping each compilation with the names it looked up outside and their status texts, `LoopNameStatus`; the first whose statuses still hold runs). The lowering's loop mode (`TJSession.LowerLoop`, `TLowerer.LoopMode`) asks `TJEntry.Outer` about non-local names: a variable whose value compiles becomes an outer variable (`TJVar.IsOuter`, listed in `TJFunction.Outers`), loaded from out slots in the prologue and, if the loop assigns it (`CollectAssigned`), stored back at the single exit (`GenOuterLoads`/`GenOuterStores`), so also after an error; a name it assigns that does not exist (or holds a value that does not compile) gets a flag register and is assigned by rule 5 afterwards only if set. `Move` never retargets an instruction into an outer variable's register, so a failing assignment leaves it unchanged. With outer variables or captures, a loop may not call anything through the interpreter (`CheckCaptures`). Written variables are moved out of their cells for the run, so arrays are not copied. `__jit_loops()` counts loops run compiled (tests). Closures and captures (J7c): reads of values from outside (names and field paths) are hidden parameters (`TJFunction.Captures`) resolved at each call by `CapturesFor` (cells cached per function object while no scope of the chain gains a name); a function with captures may not call through the interpreter; closures that assign outward are rejected, and their locally created names (`LocalNames`) must stay absent outside. `Invoke` tries `FastCall` first: compiled code with positional arguments of exactly the compiled types skips binding (no scope, cells or file switch).

## Conventions

- An uncaught error prints `Kind: message` on the first line of stderr, followed by trace lines (`  at file:line:col in function`, innermost first), and exits with code 1. The test runner relies on that first line.
- Traces are built as an error propagates: `EAxonError.Locate` records the innermost position in the current frame, and `LeaveFunction` (called in `Invoke` as an error leaves a body) names and closes the frame. An error raised with a node position should use `CreateAt`; errors without one are located by the enclosing call or statement.
- Exit codes: 0 ok, 1 uncaught Axon error, 2 usage or unimplemented feature, 3 internal error.
- REPL tests are transcripts, `tests/mNN/name.repl`, which `axon --transcript` must reproduce (trailing spaces ignored). Don't put decorative blank lines in them: every non-input line is expected output.
- Tests: `name.sci` plus `name.out`, `name.tokens` or `name.ast`; or a first line `#! error: Kind`, with an optional `name.err` that stderr must match exactly. An optional `name.in` is the test's standard input (what `input` reads). Only `.sci` files directly in `tests/mNN/` are tests; subfolders hold fixtures.
- Write expected files (`.out`, `.tokens`, `.err`) from the reference by hand, not by recording the interpreter's output, so a test can catch a real bug.
- `--tokens` prints one token per line as `LINE:COL KIND [VALUE]`. The kinds are EOF, NEWLINE, IDENT, INT (decimal value), REAL and IMAG (literal without `_`), STRING and DOCSTRING (quoted and re-escaped), KEYWORD and OP. See `src/Axon.Tokens.pas`.
- `--ast` prints S-expressions, one statement per line, with block bodies on indented lines. The full format is in the header of `src/Axon.AstDump.pas`.
- Debug builds have range and overflow checking on. `Axon.Ops` turns overflow checking off (`{$Q-}`) because it detects integer overflow explicitly and raises `OverflowError`.
- Floating-point exceptions are masked at start-up (`SetExceptionMask`), so real arithmetic follows IEEE 754 (Inf and NaN) instead of raising Delphi exceptions.
- For elementary functions whose last printed digit can differ between platforms' math libraries, tests check identities against a tolerance instead of printing 15 digits.
- Source files are UTF-8 without a byte-order mark, which Delphi reads as ANSI, so a non-ASCII character inside a string literal gets mangled. Write it as a character code instead (`#$00D7` for ×). Non-ASCII in comments is fine.
- Delphi `{ … }` comments don't nest, so a comment that contains `{` or `}` (grammar excerpts, `matrix{T}`) must use `(* … *)`.
- Parser ownership: a function that takes a child node frees it if it fails, so the caller must clear its own reference before the call. See `ParsePostfix`.

## Direction

- Over time, move more of the language onto the JIT: the interpreter stays a simple tree walker and is not being optimised (decided 2026-11-09), because most real use runs compiled code, which is 15–80× faster than CPython on loops, calls and array access while the interpreter is 25–50× slower. Records, lists and strings compile (J9–J11), and so do top-level loops (J12). Next candidates for the JIT are what it rejects most often today (survey with the JIT forced on: `AXON_JIT=force`, `AXON_JIT_LOG`): function values passed as arguments, `global`, matrix literals with vector entries, `nothing` defaults, `try`, dictionaries, closures that assign outward. Each extension needs the usual checks: compiled and interpreted results identical, tests in all three JIT modes. `bench/vs_python.py` and `bench/loops_vs_python.py` measure the effect, and the manual's appendix "Speed compared with Python" reports the numbers.
